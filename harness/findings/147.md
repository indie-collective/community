# #147 — auth-session pass

Run: 2026-09-28 with `session.mjs`, against v2 = `main` at `bef33f7` (which includes #164's `SESSION_SECRET` change) and v3 = `migration/chakra-v3` at `5f1c709`. The checklist comes from #141.

Some checks need a session the form strategy can't produce: a user with no email, as Discord can create, or a user deleted since sign-in. For those, the script mints the cookie with each app's local signing secret. As a control, it first confirms that a minted cookie for the member account is accepted: `/profile` → 200 on both.

## What works on both

- **Cookie attributes:** `HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000` (30 days). `Secure` is off locally and set when `NODE_ENV=production`.
- **Persistence:** signed in across `/`, `/games`, `/profile`, `/about` and a full reload. v3's `/events` shows the bare 500 page with no header (#145), so it can't show the user; that's not a session fault.
- **Server restart:** a cookie issued before restarting both servers still gives `/profile` → 200 afterwards.
- **Protected routes redirect when logged out:** profile, welcome, the create forms, `game.$id.edit`, the admin pages and the change history. v3 adds `?prev=`. v2 has a typo: `game.$id.edit` redirects to `?redirect=/games/:id/edit`. v3 doesn't have it.
- **Logout** clears the cookie (`Expires=1970`). v3 lands on `/signin`, v2 on `/` (#146 A11). As with any stateless cookie session, a copy of the pre-logout cookie stays valid until it expires, on both.
- **Deleted user:** a session for a user no longer in the database is bounced to `/signin` on both, and the cookie is cleared.
- **Loaders and actions agree** on the current user by construction. The vendored `Authorizer` calls the same `isAuthenticated` the root loader uses, and `canDelete` re-reads `isAdmin` from the database.
- **`isAuthenticated` no longer fails open.** #141 #3 was fixed in `5f1c709`, and anonymous requests to protected routes are refused.
- **Discord OAuth hand-off:** `POST /auth/discord` → 302 to Discord with `client_id`, `state`, and `redirect_uri=<BASE_URL or localhost>/auth/discord/callback`. A bogus callback falls back to `/signin` on both.

## Unverifiable locally

- **A full Discord sign-in** (consent → callback → session) needs a real Discord account, and the guild-membership check behind `canWrite` needs the bot token against real members. The maintainer should run it once on v3 before the merge, which is also where S3's consent screen will show.
- **Steam:** `POST /auth/steam` → 500 on both. The strategy was already commented out on `main`, so it's not a regression (#141).
